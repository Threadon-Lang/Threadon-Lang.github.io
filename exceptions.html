Exceptions

how failure works when nothing can catch it

No catchable exceptions

Threadon has no try, except, raise or throw. There is no stack unwinding, no exception object travelling back to a caller, and no error value that a function can silently pass upward.

An operation either succeeds, is rejected by the compiler before anything runs, or stops the process. There is no fourth path where your code catches a failure and carries on from the middle of an expression.

Don't translate Python-style exception handling directly. Check the condition before performing the operation that could fail.

Compile-time errors

Most mistakes are caught before a program exists: type mismatches, unknown names, wrong argument counts, missing return statements, invalid imports, and out-of-range literals. The compiler prints the message, the line, and a caret pointing at the problem.

Error: If condition must be Bool, got Int32 at line 3
      if x:
      ^

A compile-time error produces no executable and runs nothing. See Basics for what the messages look like.

Runtime failures

Some failures depend on values the compiler cannot know. With --debug, Threadon inserts checks for them. When a check fires, the process prints a [RUNTIME ERROR] block to stderr and exits with code 1.

  • Integer division or modulo by zero.
  • A String that does not start with a number when converting to Int32, Int8 or Float32.
  • Integer results outside the target type's range.
  • Reading past the end of a list or string, or looking up a missing dict key.
  • Non-finite floats when --flag-inf is enabled.
[RUNTIME ERROR]
│ Error: Division by zero
├─> Location: (null)
└─> Process terminated with exit code 1

The full list and the exact messages are on the Debug page. Without --debug, most of these checks are absent and the behavior is undefined. --flag-inf is independent of debug mode.

Exit codes

The value returned from main becomes the process exit code. Return 0 for success. A runtime check failure exits 1. A compile-time error never starts a process at all.

A library function cannot throw an exception that changes the exit code. If a call can fail, return a status value and let main choose the exit code.

Handling failure without exceptions

Check first. Test the divisor before dividing, compare an index with len(xs) before indexing, and validate a string before converting it. These checks work in release builds too, where the debug runtime checks are not present.

def safe_div(a: Int32, b: Int32) -> Int32
    if b == 0:
        return 0
    return a // b

def main() -> Int32
    print(safe_div(10, 2))
    print(safe_div(10, 0))
    return 0
5 0

When the caller needs to tell success from failure, return a sentinel, a struct with an ok flag, or a union. Threadon has no built-in Result or Option type, but you can define one as a struct.
