Threadon / Garbage collector

Garbage collector

explicit, conservative, non-moving

What it does

Threadon has an explicit, manual garbage collector. There is no free in the language. The built-in collect() function runs a full collection synchronously on the calling thread before returning. It takes no arguments and returns NoneType.

Nothing is collected automatically. There is no background collector thread, no allocation threshold and no THREADON_GC_THRESHOLD environment variable. A program that never calls collect() never runs a collection, even if it allocates heavily. The collector is conservative and non-moving: payload words are scanned without type descriptors and live objects never change address.

What is collected

Every heap allocation emitted by the compiler goes through __threadon_gc_alloc:

  • string concatenation, slicing and chr
  • list and dictionary backing arrays
  • thread closure structs
  • template payloads and template objects

String literals are static constants and are not collected. Memory owned by native modules (C/C++/Rust/Python objects) stays owned by those modules. Structs and list/dict descriptors themselves are LLVM aggregate values; only their heap backing arrays are GC blocks.

Call collect() at points where you know a batch of temporary values has become garbage: between loop iterations, after dropping a large list, or before a memory-sensitive phase. Allocations between calls are not reclaimed until the next call.

Example

This loop builds a new string on every iteration; the old buffers become garbage. Calling collect() periodically keeps memory bounded:

def main() -> Int32
    s: String = ""
    i: Int32 = 0
    while i < 8000:
        s = s + "x"
        if i % 100 == 0:
            collect()
        i += 1
    print(len(s))
    collect()
    return 0
8000

How collection works

Each block has a 48-byte header (magic, size, mark epoch, links) followed by the payload pointer handed to generated code. The payload is scanned word by word: a word counts as a pointer when it looks like a valid heap header. That avoids emitting precise type descriptors for every container type.

Roots come from three places:

  • module globals, registered by the generated main wrapper
  • per-thread stack snapshots, scanned conservatively up to a high-water mark
  • heap slots, handled by a write barrier after pointer stores into GC objects

There are no LLVM stack maps and no shadow stack.

One collect() call has four phases, all on the calling thread:

  1. It bumps the mark epoch and snapshot generation, then snapshots the calling thread's stack. Other threads use snapshots they published when they last allocated.
  2. It marks module globals and all published snapshots, following pointers found inside marked payloads.
  3. It takes a second snapshot generation to catch pointers written into locals during step 2, then marks again.
  4. It sweeps unmarked blocks. Blocks allocated during the cycle are born already marked, and pointer stores into heap objects mark the new value, preserving the tri-color invariant.

Stats

There is nothing to tune for triggering: collection happens only when you call collect(). One optional environment variable controls diagnostics:

VariableDefaultEffect
THREADON_GC_STATSoffany value except exactly 0 prints timing stats at exit
THREADON_GC_STATS=1 python3 -m threadon app.th --run

With stats enabled, the program prints a line like this at exit (timings vary per run):

[gc] collections=81 snapshots=162 snapshot_max=0us snapshot_avg=0us mark_max=52us sweep_max=812us collector_total=8.4ms

collections is the number of explicit collect() calls. snapshot_* is the time spent publishing root snapshots; mark_max and sweep_max are the longest single phases; collector_total is the sum of all collection time.

Implementation notes

The collector lives in gc_runtime.c next to the compiler sources. build_gc_runtime.sh compiles it with clang to gc_runtime.ll, strips module/target lines and renames private string constants so they cannot collide with generated ones. The IR is appended to a module when it allocates or calls collect(), which keeps lli and native executables identical.

The longer design note is GC.md in the same directory.

Notes and gotchas

  • Conservative scanning can keep an object alive for one extra cycle if an integer happens to look like a heap pointer.
  • A collect() call pauses the calling thread for the whole mark-and-sweep cycle; there is no background marker or sweeper.
  • Other threads keep running, but briefly lock around heap bookkeeping and snapshot publication. New allocations during a cycle are safe.
  • A thread that blocks forever or never allocates again keeps its last published snapshot; a collection proceeds with whatever snapshots are available.
  • The collector does not move objects, so native pointers into live Threadon strings or lists remain valid.
  • Fixed caps: 128 registered threads, 8192 snapshot words per thread and 256 global roots. Entries past those caps are ignored.
